# 评测方法，以及评测自己的盲区

## 评测集设计

33 条用例，刻意分层，覆盖不同难度：

| 类型 | 数量 | 说明 |
|---|---|---|
| `seed-code` | 10 | 带完整报警码与面板文字，测规则直出 |
| `seed-symptom` | 10 | 纯口语症状，无报警码，测检索 |
| `真实工单` | 13 | 现场真实描述，含错别字与省略 |

每条用例的字段：

```csv
id,symptom,expected_code,expected_category,expected_cause_keywords,expected_action_keywords,source,note,leaked
```

## 四个指标

| 指标 | 测什么 | 当前值 |
|---|---|---|
| **L0 命中** | 带码问题，规则层直接命中正确的码 | 14/15 = 93% |
| **检索 Top-1** | 无码问题，排名第一的片段是否对应正确故障 | 12/18 = 67% |
| **检索 Top-3** | 同上，前三名内是否命中 | 15/18 = 83% |
| **分类准确率** | 预测的故障大类是否正确 | 23/33 = 70% |

外加两项工程指标：**平均延迟 8ms**、**评测集与知识库重叠 0**。

## 防泄漏为什么单独列一项

如果评测题就在知识库里，所有指标都是自欺。

`check_leak.py` 的做法：把评测集的 symptom 和知识库的 `cause + confirm` 做字符二元组重合检测，重合度超阈值即判定泄漏，把 `leaked` 列标 1 并从计分中剔除（`mark_leaked.py`）。

当前结果：

```
eval: 33 | cases: 17 | overlap: 0
```

**0 泄漏**，说明这 33 条题是真的在考系统，不是背答案。

## 评测的结构性盲区

这套评测测的是"**有没有找到对的码 / 对的片段**"。

它完全没有测"**下一步该查什么**"。

因为后者没有标准答案——同一个故障，两个老师傅的排查顺序可能都不一样。

于是出现一个荒谬的局面：

> 我能用 33 条题证明检索是好的，却**没有任何一条题能证明我的诊断建议是对的**。

那个功能只能靠模拟评估，而模拟的结果（降幅 1%）改变了整篇文章的结论。

## 教训

**评测覆盖什么，就会优化什么；没被评测覆盖的层，会悄悄烂掉。**

如果你在做一个有"决策层"的 AI 产品，评测必须往决策层延伸——哪怕只能用模拟或专家打分，也胜过不测。
