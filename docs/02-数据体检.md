# 数据体检：243 条规则里的五类脏数据

> 结论先行：**RAG 的准确率再高，也只是更准确地捞出一堆脏东西。**

## 体检方法

三支脚本，三种粒度：

| 脚本 | 检查项 | 粒度 |
|---|---|---|
| `audit_rules.py` | 串码 / 未拆分 | 码级 |
| `kb_dedupe.py` | 重复 / 疑似重复 / 冲突 | 原因级（字符二元组 Jaccard） |
| `check_leak.py` | 评测集泄漏 | 数据集级 |

```bash
python audit_rules.py
python kb_dedupe.py
python check_leak.py
```

## 五类脏数据

### 1. 串码

同一个错误码底下混着多套互不相干的原因组。

例：`E108` 系列共享硬件码 `0x5530`，但覆盖写入异常、读取异常、校验错误三条不同排查路径。

`audit_rules.py` 的判定规则：同一码下出现多组 `1.` 开头 → 串码。

### 2. 未拆分：25 个码

原因字段填的是 `（手册未拆分原因，见第 16 章）`。

`E108.2` 即其一。用户问到这些码，系统只能回答"按手册 16.6 排查"——把问题原封不动退还给用户。

### 3. 判据为空：26 个码

`confirm` 字段为空。系统能列出可能原因，但无法说明**先查哪个、怎么确认**。

而后者正是现场最花钱的部分。

### 4. 字段语义混淆（最危险）

`verify`（处置可验证性）与 `check_type`（检查成本）**取值域完全相同**（实测/观察/替换），语义完全不同：

| 字段 | 回答的问题 | 用途 |
|---|---|---|
| `verify` | 修完之后怎么确认修好了 | 处置闭环 |
| `check_type` | 查这条原因要花多少成本 | 排序与推荐 |

混用后果：**把"换驱动器"（成本 5.0）当成"实测"（成本 1.0）推荐给你。**

而且这个 bug **静默**——两个字段取值域同构，永不抛异常，只会默默算错。

```python
# 错误写法：拿 verify 当成本
cost = COST.get(row["verify"], 1.5)

# 正确写法：成本一律取 check_type，缺失才回退
cost = COST.get(row["check_type"] or row["verify"] or "观察", 1.5)
```

### 5. 非法枚举：49 行

`verify = 未分类`。

程序不报错，成本表查不到就 fallback 到默认值，**静默按最便宜的档算**。

## 审计自己的盲区

跑完 `audit_rules.py`，输出是：

```
① 串码：无
② 未拆分：无
审计完成。
```

但**通过是假的**——那 25 个占位码，审计一个都没抓到。

原因：审计规则写的是"一个 cause 含两个及以上连续序号"，而占位符是纯文本，没有序号。

> **教训：「检查通过」和「数据是好的」是两件事。检查通过只说明「我的检查项没命中」。**
